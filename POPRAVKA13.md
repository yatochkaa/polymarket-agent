§1. Спред-издержка для ретроспективы (только /trades)
=====================================================
§1.1 — Прямая констатация. Несмещённой точечной спред-издержки из /trades не существует: есть
исполненные цены и сторона, но не покоящиеся котировки; без стакана (POPRAVKA4:22) уплаченный
полуспред не идентифицируется. Ниже — прокси, знак смещения которого установлен по данным ночного пересчёта: измеренное смещение оценки — ВНИЗ (доля отрицательных сырых разниц vwap_buy − vwap_sell составляет 14–31% и монотонно растёт с порогом отбора; при клемпе max(·,0) это ЗАНИЖАЕТ оценку полуспреда). Занижающий прокси не является автоматически консервативным к GO, поэтому консервативность обеспечивается не знаком прокси, а надбавкой к SE_cost для импутированных пар (§1.4) и гейтом UNDECIDABLE, а не занижением точечной оценки. Спред входит как точечная компонента cost и вклад в SE_cost (§3), не в bracket_width
(ПР:31 — только зазор гипотез комиссии).

Единицы и таймстемпы (операциональная преамбула для §1.2 и §4.4).
- ВСЕ таймстемпы (timestamp сделок, gameStartTime, e_min, e_max, границы окна) — юникс-СЕКУНДЫ
  (целые секунды от эпохи; в этом датасете ~1.77e9). Ни миллисекунд, ни иных единиц не используется.
- D — полуширина окна в МИНУТАХ. D_WORK = 60, D_ALT = 10.
- Перевод в секунды СТРОГО через множитель 60: D_sec = D * 60. (НЕ 60000; 60000 = мс/мин и в
  секундном времени запрещён.)
- Обязательная страховка единиц перед сбором любого пула: реализация проверяет, что
  median(e_min) ∈ [1e9, 2e10] (секунды, а не мс ~1e12) и что D_sec == D*60. Нарушение любого — STOP.

§1.2 — Оценщик эффективного полуспреда (операционально; без самоссылки, Поправка 7 §2).
Единица наблюдения — пара (кошелёк w, матч m). Сторона входа a = outcomeIndex сделок входа w на m.

(1) Размах входов (юникс-секунды):
      e_min = min(timestamp входных сделок w на m по стороне a)
      e_max = max(timestamp входных сделок w на m по стороне a)

(2) Границы окна для полуширины D минут (буквально, множитель — ровно 60, секунды):
      lo(D) = e_min − D*60
      hi(D) = e_max + D*60

(3) Окно W_{w,m}(D) — ЗАКРЫТЫЙ интервал, ОБЕ границы включительно, пересечённый с предматчем:
      W_{w,m}(D) = { t : lo(D) <= t <= hi(D)  И  t < gameStartTime(m) }
      prematch(t) ⇔ t < gameStartTime(m) — замороженное определение предматча.
      Включительность задана явно: и левая точка (t == lo(D)), и правая (t == hi(D)) принадлежат
      W_{w,m}(D) (оба сравнения — нестрогие <=).

(4) Пул P_{w,m}(D) — предикат фильтрации. Сделка x ∈ P_{w,m}(D) тогда и только тогда, когда
    выполнены ВСЕ строки (конъюнкция, ни одна не опускается):
      x.conditionId == conditionId(m)          # тот же рынок
      x.asset       == token(a)                 # тот же токен стороны a
      x.proxyWallet != w                         # исключение самоссылки (Поправка 7 §2)
      x.timestamp   <  gameStartTime(m)          # предматч, замороженное определение
      lo(D) <= x.timestamp <= hi(D)              # попадание в W_{w,m}(D), обе границы включительно

(5) Разбиение P_{w,m}(D) по side: BUY (снят ask), SELL (снят bid).
      vwap_buy(D)  = Σ price*size / Σ size по BUY
      vwap_sell(D) = Σ price*size / Σ size по SELL
      eff_spread(w,m,D)        = max(vwap_buy(D) − vwap_sell(D), 0)
      spread_cost_point(w,m,D) = 0.5 * eff_spread(w,m,D)        # на share
    Рабочее значение оценщика — на рабочем окне:
      spread_cost_point(w,m) = spread_cost_point(w,m, D_WORK=60).
    Обозначения: W₆₀ = W_{w,m}(D) при D=60, W₁₀ = W_{w,m}(D) при D=10.

Требование о сужении (анти-артефакт единиц). При корректных единицах W₁₀ строго уже W₆₀, поэтому
P_{w,m}(10) ⊆ P_{w,m}(60), и на нетривиальном предматче (span ≫ 2*D_WORK) для большинства пар
P_{w,m}(10) ⊊ P_{w,m}(60). Совпадение пулов P_{w,m}(10) == P_{w,m}(60) поэлементно по ВСЕМ парам —
признак ДЕФЕКТА (почти всегда — окно в неверных единицах, накрывшее весь предматч), а НЕ свойство
данных. Фильтр по окну обязан реально сужать выборку; проверка вынесена в §4.4 как блокирующая
(§4.4-guard).

§1.2-bis — Входы на обоих токенах (усреднение по size). Если w имеет входные сделки на ОБОИХ
токенах стороны (a ∈ {0,1}), spread_cost_point(w,m) считается по каждому токену отдельно на его
пуле P_{w,m,a}(D_WORK) и усредняется по size входов w:

      S_a = Σ size входных сделок w на m по токену a

                            Σ_a  S_a * spread_cost_point_a(w,m, D_WORK)
      spread_cost_point(w,m) = -------------------------------------------------
                                        Σ_a  S_a

где spread_cost_point_a(w,m, D) = 0.5 * max(vwap_buy_a(D) − vwap_sell_a(D), 0), а пул P_{w,m,a}(D) —
предикат (4) с x.asset == token(a). Весами служат size входов w на m по соответствующему токену
(НЕ число сделок и НЕ суммарный объём пула). Для одного токена формула вырождается в §1.2(5).
Порядок операций (уточнение, важно). Обрезка max(vwap_buy − vwap_sell, 0) применяется ВНУТРИ каждого активного токена (в spread_cost_point_a), и лишь ПОСЛЕ неё выполняется усреднение по весам size. Обратный порядок (усреднение знаковых разниц по токенам с обрезкой в конце) неверен и запрещён. По данным пересчёта прежний порядок затрагивал 693 пары из 449 342 — все двухтокенные, — с максимальным сдвигом оценки 0.057.

§1.3 — Смещение прокси и предрегистрация детрендинга (две ветви, обе написаны ДО чисел).
Прокси vwap_buy − vwap_sell искажается внутриоконным дрейфом вероятности (тренд имитирует
спред). По данным пересчёта чистое смещение оценки — ВНИЗ (§1.1), поэтому оно НЕ консервативно к GO само по себе; консервативность несёт надбавка к SE_cost (§1.4), а дрейф как конфаундер контролируется тестом §4.4b и §4.4-guard. Детрендинг может либо не применяться, либо
включаться принудительно. Обе ветви фиксируются ЗАРАНЕЕ (это и есть предрегистрация); конкретная
ветвь выбирается ПОСЛЕ прогона §4.4 по правилу ниже — не по взгляду на clv.
  • Ветвь A — «детрендинг ВЫКЛЮЧЕН» (по умолчанию). Выбирается, если §4.4-guard пройден
    (n_pool_diff > 0) И не сработал ни §4.4a, ни §4.4b (в частности |M*| ≥ 200). Тогда
    spread_cost_point(w,m) берётся как в §1.2 без вычитания тренда; консервативность обеспечивается
    надбавкой к SE_cost (§1.4), а не знаком точечной оценки.
  • Ветвь B — «детрендинг ВКЛЮЧЁН принудительно». Выбирается, если сработал §4.4a ИЛИ §4.4b
    (включая безусловный случай |M*| < 200). Тогда в каждом окне перед расчётом vwap_buy/vwap_sell
    из цены вычитается робастный внутриоконный тренд — медианный наклон цены по времени
    (Theil–Sen, медиана попарных наклонов), — после чего §4.4a и §4.4b прогоняются заново и ветвь
    переопределяется по обновлённым числам.
  • STOP по §4.4-guard (n_pool_diff == 0) не выбирает ни A, ни B: это неисправный инструмент
    (единицы §1.2). Сначала правится код окна, затем §4.4-guard и оба теста повторяются.
Пол оценки (обе ветви): spread_cost_point(w,m) ≥ 0 и не ниже минимального наблюдаемого шага цены
рынка; клемп ≤ 0.5.

§1.4 — Нехватка двусторонней ликвидности: импутация, а не исключение.
Измеримость пары (единое определение, одинаково в §1.4, §4.4a и §4.4b). Порога N_min нет: оценщик применяется везде, где математически определён. Проверка идёт ПО КАЖДОМУ АКТИВНОМУ ТОКЕНУ a пары (w,m) ОТДЕЛЬНО, и результаты соединяются через И. Активный токен a — тот, по которому у кошелька w положительный суммарный размер входа на матче m (S_a > 0). Пара (w,m) ИЗМЕРИМА при D тогда и только тогда, когда для КАЖДОГО активного токена a в пуле есть минимум одна покупка И минимум одна продажа на не-self сделках в W_{w,m}(D) (n_buy(a) >= 1 И n_sell(a) >= 1). Достаточно одному активному токену не иметь хотя бы одной покупки или хотя бы одной продажи — пара неизмерима при D целиком.
Если пара (w,m) НЕИЗМЕРИМА при D в этом смысле (у какого-либо активного токена нет хотя бы одной покупки или хотя бы одной продажи в W_{w,m}(D)), спред для неё напрямую не оценивается ⇒ П13 импутирует spread_cost_point(w,m) = МЕДИАНА измеренных значений по парам того же тира с данными (НЕ p90); пара помечается флагом.
Почему медиана, а не p90. Медиана оценщика инвариантна к порогу отбора на всём диапазоне 1..20 (0.005 = полтика тиковой сетки), тогда как p90 меняется втрое (0.0135 → 0.05). Значит p90 — свойство правила отбора, а не рынка; импутация обязана опираться на инвариант, поэтому берётся медиана тира.
Куда переносится консервативность. Не в завышенную точку, а в SE_cost: для каждой импутированной пары в дисперсию cost добавляется эмпирический разброс ИЗМЕРИМОГО распределения того же тира (§3). Следствие: массовая импутация РАСШИРЯЕТ интервал и толкает вердикт к UNDECIDABLE, а не производит уверенный NO-GO из константы. Прежняя редакция (порог N_min = 20, импутация по p90 = 0.05 против median(|clv|) = 0.02) предрешала NO-GO арифметикой независимо от данных — эта редакция дефект устраняет.
Почему импутация, а в Поправке 8 — исключение. В П8 недоказуемой была сама валидность наблюдения
(предматч-полнота рынка под вопросом) ⇒ исключение целого рынка (ограниченно, MAX_EXCLUDED=20) без
смещения оценки выживших. Здесь наоборот: CLV пары полностью измерим, недоступна лишь поправка на
спред. Исключение выкинуло бы валидное CLV-наблюдение по признаку ликвидности ⇒ селекция на
ликвидность (систематическая потеря неликвидных матчей, ликвидность может коррелировать с edge) —
смещение gross_delta. Импутация консервативного верха сохраняет наблюдение и лишь удорожает cost
(смещение против GO). Поэтому здесь селекция опаснее импутации — выбор противоположен П8 осознанно.
Отчётность. В воронку sec.7d добавляется строка пар с импутированным спредом (пара, у которой хотя бы у одного активного токена нет двусторонней ликвидности — нет покупки или нет продажи в окне):
N (по тирам и итого).

§1.5 — Допущение о роли кошелька (тейкер/мейкер). В /trades нет контрагента, поэтому роль кошелька
в сделке из /trades не определима: неизвестно, был он тейкером или мейкером. Мейкер полуспред не
платит (получает), а комиссия у Polymarket только тейкерская (fees.py:8, 198–203). П13 вменяет всем
входам полуспред (§1.2) и тейкерскую комиссию (§2). Явная формулировка: «роль кошелька в сделке из
/trades не определима; принимается наихудший для GO вариант — тейкер на обеих компонентах (спред и
комиссия)». Это консервативное допущение, а не факт; при заморозке оно записывается в ASSUMPTIONS.md.


§2. Численная привязка комиссии и bracket_width (по fees.py)
============================================================
§2.1 — Ставка и формула. Теннис ⇒ Vertical.SPORTS ⇒ feeRate = 0.05 (доля, fees.py:57).
fee = C·feeRate·p·(1−p) (fees.py:7). На share:
  shares:  φ_S(p) = feeRate·p·(1−p)   (fees.py:154–155);
  notional: φ_N(p) = feeRate·p²·(1−p) (fees.py:158–159).
φ_S ≥ φ_N на (0,1) ⇒ high=shares, low=notional (fees.py:227). Само-проверка p=0.20: φ_S=0.008,
φ_N=0.0016, отношение 5× — сходится с fees.py:15.
§2.2 — bracket_width на share. β(p) = φ_S(p) − φ_N(p) = feeRate·p·(1−p)² — FeeQuote.bracket_width
(fees.py:89), нормированный на share.
§2.3 — Исправление некогерентности единиц в ПР:44. FeeQuote.bracket_width в USD (fees.py:88),
gross_delta — доля на share (ПР:29). П13 фиксирует: обе величины берутся на share (USD-значение
делится на shares). Это устранение некогерентности единиц в ПР:44, не изменение формулы ПР:37 и не
переопределение FeeQuote; смысл ПР:31 сохраняется дословно.


§3. Вход cost и bracket_width в замороженный агрегатный критерий
===============================================================
Единица решения и семья BH (POPRAVKA7:81, 111–114). Один тест на кошелёк; тиры не смешиваются в
оценке, но объединяются в семью. Семья FDR q=0.10 = кошельки ATP и WTA вместе, прошедшие допуск §5
в своём тире; оценка кошелька ведётся внутри его тира. Единица наблюдения внутри теста — матч (ПР:25–26).
Для кошелька w (в его тире), усреднение по матчам как у gross_delta:
  gross_delta_w — среднее CLV на share по матчам (заморожено).
  cost_w = fee_point_w + spread_point_w (ПР:30): fee_point_w = среднее по матчам φ_S(entry_vwap_m)
    (верхняя shares-база); spread_point_w = среднее по матчам spread_cost_point(w,m) (§1).
  bracket_width_w = среднее по матчам β(entry_vwap_m) (только зазор комиссии).
  SE_edge_w — кластерный SE CLV (заморожено, ПР:32/71–72).
  SE_cost_w — кластерный SE спред-компоненты (комиссия при фиксированной базе детерминирована ⇒
    нулевая выборочная дисперсия; для импутированных пар §1.4 в дисперсию добавляется эмпирический разброс измеримого распределения того же тира).
Порядок исходов (ПР:43–46, дословно): 1) UNDECIDABLE, если bracket_width_w > gross_delta_w;
2) GO, если gross_delta_w − cost_w > 2.5·√(SE_edge_w² + SE_cost_w²); 3) NO‑GO иначе.

Верхняя (shares) база — прямое следствие H1. ПР:21 формулирует H1 как «gross_delta − cost > 0
устойчиво к неопределённости базы комиссии». Устойчивость односторонней гипотезы (ПР:23) к

ПР:21, не конвенция. Остаточный зазор φ_S − φ_N несёт bracket_width и срабатывает гейтом

Проверка идёт ПО КАЖДОМУ АКТИВНОМУ ТОКЕНУ a пары (w,m) ОТДЕЛЬНО, и результаты соединяются через И. Правило (предобъявлено): если эта медиана > 0.025 (пять минимальных полуспредов), оценщик признаётся неправдоподобным
как измеритель спреда.

§4.4-guard — ОБЯЗАТЕЛЬНАЯ проверка невырожденности окна (ДО отношения §4.4b; блокирующая).
Смысл: тест на дрейф сравнивает оценщик на W₆₀ и W₁₀. Если окна физически совпадают, отношение
тождественно 1.0 и тест невозможно провалить — а тест, который нельзя провалить, тестом не является.
Единицы (исправление). Обе сравниваемые в guard величины измеряются в ПАРАХ. Прежняя редакция
сопоставляла n_pool_diff (число ПАР) с n_band (число СДЕЛОК) — величины в несопоставимых единицах,
требование было некорректным; здесь оно заменено на сравнение пар с парами.
Правило (исполняется ПЕРЕД вычислением отношения §4.4b):
  (i)   для каждой пары (w,m) вычислить P_{w,m}(10) и P_{w,m}(60) по §1.2(4) и сравнить их
        поэлементно (по множеству transactionHash сделок);
  (ii)  n_pool_diff = число ПАР, у которых пул при D=60 строго шире пула при D=10
        (P_{w,m}(10) ⊊ P_{w,m}(60): при уменьшении окна пул реально сузился);
  (iii) n_band_pairs = число ПАР, у которых полоса между окнами [lo(60),lo(10)) ∪ (hi(10),hi(60)] непуста;
  (iv)  ТРЕБОВАНИЕ невырожденности: n_band_pairs == n_pool_diff (обе величины — в парах), И ни у одной
        пары пул D=60 не меньше пула D=10 (P_{w,m}(10) ⊆ P_{w,m}(60) всюду);
  (v)   нарушение (в частности n_pool_diff == 0) ⇒ STOP с диагностикой, а НЕ вывод «дрейфа нет».
        Диагностика STOP печатает: median(e_span = e_max−e_min, сек); median предматч-span (сек и
        часы); lo(10)/hi(10) и lo(60)/hi(60) на примере; D_sec для обоих D; напоминание проверить
        единицы (D*60, а не D*60000; e_min в секундах);
  (vi)  отношение §4.4b считается ТОЛЬКО после прохождения (iv).
ИЗМЕРЕНО (воспроизведено дважды, на всех шести порогах измеримости): n_band_pairs == n_pool_diff = 247522
(247522 = 247522); пул D=60 нигде не меньше пула D=10 (ноль строк-нарушений). Guard ПРОЙДЕН.
Справочно: n_band = 10 555 817 сделок (совокупное число сделок в полосах; величина в СДЕЛКАХ, в
проверке guard НЕ участвует).
