# Оболочка, кодировки, живость процесса

Большинство потерянного времени — не логические ошибки, а команды, которые не
исполнились, вывод, который не появился, и процессы, которые казались живыми.

## Готовый блок для вставки

- Один ответ — один готовый блок. Не давай два варианта на выбор.
- Если блок дан для чтения, а не для исполнения (например, дифф) — подпиши его
  «только глазами». Вставленный в консоль дифф не меняет ничего, но выглядит
  как работа.
- Всегда говори, сколько блок работает и что будет на экране. Перенаправленный
  вывод — пустой экран по замыслу, об этом надо предупредить заранее.
- Называй точный путь к файлу и то, кому уходит вывод, если исполнителей
  несколько.
- Перед отправкой блока проверь: пути существуют и без опечаток, команды
  соответствуют ИМЕННО той оболочке, которая у владельца, все допущения о
  именах колонок/полей/функций уже подтверждены дешёвой командой.

## Windows PowerShell (частый случай)

- `cd /d` — это cmd, а не PowerShell.
- `>` в PowerShell 5.1 пишет UTF-16; читать такой файл надо
  `Get-Content X -Encoding Unicode`. Лучше сразу `Tee-Object -FilePath`.
- Вставка ломает `$_`. В блоках для вставки не использовать `$_` вообще:
  вместо выражений с `$_` пиши `Get-Item <файл> | Format-List Length, LastWriteTime`.
- Кодировка перед запуском чего-либо с не-ASCII выводом:

```powershell
chcp 65001 > $null
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
$OutputEncoding = [System.Text.Encoding]::UTF8
$env:PYTHONUTF8 = "1"
$env:PYTHONIOENCODING = "utf-8"
```

- В логах длинных прогонов пиши сообщения латиницей. Смешанные кодировки в
  логе делают поиск по национальному тексту бессмысленным; искать надо по
  ASCII-якорям (`ERROR`, `stats:`, имена исключений).
- Фильтры в поиске по логу с битой кодировкой задавай без `-Encoding`:
  указание кодировки может дать пустой вывод при непустом `.Count`.

| Unix | PowerShell |
|---|---|
| `grep -n X f` | `Select-String -Pattern X -Path f` |
| `grep -rn X` | `Get-ChildItem -Recurse -Filter *.py \| Select-String X` |
| `sed -n '30,50p' f` | `Get-Content f \| Select-Object -Skip 29 -First 21` |
| `tee f` | `Tee-Object -FilePath f` |
| `cat f` | `Get-Content f` |
| `mkdir -p d` | `New-Item -ItemType Directory -Force d` |
| `tail -n 3 f` | `Get-Content f -Tail 3` |
| `wc -l f` | `(Get-Content f).Count` |

## Скрипты, передаваемые через вставку

- Никаких f-строк и вложенных кавычек: они дают синтаксические ошибки при
  переносе через буфер обмена.
- Скрипт, импортирующий пакет проекта, требует либо переменной пути в том же
  блоке, либо bootstrap пути внутри самого скрипта. Иначе `ModuleNotFoundError`.
- Запуск без буферизации (`python -u` и аналоги), иначе тишина выглядит как
  зависание.
- Проверка компиляции доказывает синтаксис, а не поведение. Скрипт без точки
  входа завершается молча и с кодом 0. Всегда убедись, что появилась ПЕРВАЯ
  строка вывода.
- Поиск определений по шаблону `^def ` пропускает `async def`. Ищи оба.

## Жив ли процесс

Существование процесса не значит, что он работает. Проверяй три вещи:

1. процесс есть и сколько он съел процессорного времени;
2. размер и время изменения его выходных файлов;
3. те же размеры через 60–90 секунд.

Два одинаковых замера размера — это смерть, даже если процесс в списке.
Рост процессорного времени БЕЗ роста файлов — это цикл без выхода, а не
сетевое ожидание: висящее ожидание не тратит процессор вовсе. Прежде чем
назвать что-то зависшим, посмотри счётчик CPU.

Сообщение «процесс с таким именем/идентификатором не найден» — это
окончательное «ничего не запущено», а не ошибка команды.
